# 学習ローグ 配置型TCG カード効果「唯一無二」再設計計画

## 1. 目的

配置型TCGに存在する全カードについて、現在の効果構造を整理し、**各カードが名前・役割・使い方まで含めて他のカードと明確に区別できる固有効果**へ再設計する。

この文書は、今後カード効果を実装修正するときの設計基準・監査基準・実装順を定めるためのものとする。カード画像、カード名、対戦相手、基本ルールはこの作業では変更しない。

## 2. 現在のカード総数

現行 `PLACEMENT_TCG_CARDS` は **584枚**。

| Edition | UNIT | SUPPORT | EVENT | 合計 |
| --- | ---: | ---: | ---: | ---: |
| ELEMENTARY | 128 | 33 | 34 | 195 |
| HIGH_SCHOOL | 121 | 33 | 33 | 187 |
| MAGIC | 135 | 34 | 33 | 202 |
| **合計** | **384** | **100** | **100** | **584** |

カードIDの重複はない。表示名は現在1組だけ重複しており、次の2枚がどちらも「バスケ部エース」になっている。

- `MTCG_HIGH_SCHOOL_HERO_DODGEBALL`
- `MTCG_HIGH_SCHOOL_ENEMY_092`

効果の固有化を進める際は、IDを正として別カードとして扱う。

## 3. 現在の効果構造

現行カードは、実質的に2層の効果を同時に持っている。

1. `effect` + `amount` による従来効果
2. `effectProgram` による2ステップの固有DSL効果

カード表示の `rulesText` も、この2層を連結して表示している。

### 3.2 `effectProgram` は584枚すべて別シグネチャ

現行DSLは次の要素を組み合わせている。

- trigger: 最大9種
- action: 14種
- target: 10種
- condition: 9種
- resetRule: 3種
- 1カードにつき2 step

現在の `normalizedSignature` は **584 / 584 がユニーク**で完全重複はない。さらに数値と `duration` を除外し、`kind + trigger + resetRule + action + target + condition` だけでEditionをまたいで比較しても584件すべて別になっている。

ただし、この結果だけでは「プレイ体験として唯一無二」とは判定しない。

## 4. 現在の問題点

### 4.1 カード名やテーマではなくindexから効果が決まる

`buildPlacementEffectProgram()` はカードの意味や名前ではなく、主に `index` と `amount` の計算で trigger / action / target / condition を決めている。

そのため、数式上は全カードが違っていても、カード名から期待される挙動とのつながりが弱い。今後は**名前・キャラクター性・元カードのイメージ・Editionの方向性から手作業で決める**。

### 4.2 `duration` は攻撃力 / 体力の時限強化として実装済み

Phase 0で `BUFF_ATTACK` / `BUFF_HEALTH` の `duration` を実戦へ反映した。`duration=N` は「効果解決後に利用できる自分ターンの行動窓をN回分」とする。自分の `TURN_END` または相手ターン中に付与された場合は、次の自分ターンを1回目として数える。

それ以外のactionでは `duration=0` へ正規化し、意味のないduration差をカード固有性として数えない。相手ターン中に付いた `duration=1` が2回の自分ターンに残る境界不具合も回帰テスト付きで修正済み。

### 4.3 MARKの多くがゲーム上ほぼ意味を持たない

`MARK` は116 step存在するが、そのうち91 stepは同一プログラム内に `AFTER_MARK` を使う後続処理がない。さらにMARK用メモリはカードインスタンス固有なので、他カードとの連携にも使われない。

MARKを残すカードは、必ず次のどちらかを満たすこと。

- 同じカードの後続stepまたは次回triggerで `AFTER_MARK` を使う
- 今後追加する共有タグ・レーン状態など、別の明確な参照先を持つ

### 4.4 `REORDER_HAND` が説明と実装で一致しない

用語説明では「手札を山札に戻して引き直す」となっているが、現行実装は手札配列の順番を回転させるだけである。手札の順番自体にゲーム上の意味がほぼないため、39 stepある `REORDER_HAND` は実質的に弱い、または無作用に近い。

再設計前に次のどちらかへ統一する。

- 本当に手札交換・マリガンとして実装する
- action自体を別の有効な手札操作へ置き換える

### 4.5 `OWN_ANY` / `ENEMY_ANY` は「選択」ではなく先頭を自動対象にする

表示上は「味方1体」「敵1体を選ぶ」と読めるが、現行 `laneTargets()` は左から最初に見つかったユニットを自動選択する。

カード固有効果に「対象選択そのもの」を戦術性として使う場合は、プレイヤーが対象を選べる処理を先に実装する。

### 4.6 FINISH効果は勝敗決定後に発動する

`FINISH` trigger は42枚に存在するが、相手ライフが0になり勝者が決まった後に発動する。現状では勝敗へ寄与しないため、カードの主効果としては弱い。

FINISHは次のような用途に限定する。

- 演出専用
- ラン内報酬や次戦ボーナスなど、勝利後にも意味がある効果
- 勝敗確定前に解決する新しい「致命打」triggerへ仕様変更する

### 4.7 従来効果とDSL固有効果が同時発動する

現在は `effect` の処理後に `effectProgram` も解決される。結果として、1枚に「共通能力 + 自動生成2step」が乗り、カードの主役となる能力が分かりにくい。

再設計後は**1枚につき主役となる効果コンセプトを1つ**決め、そのコンセプトの中に必要な複数stepを含める。

### 4.8 発動回数・対象・撃破元にも実装ずれがある

個別カードを584枚設計する前に、次の共通挙動を修正する。ここが曖昧なままだと、同じ効果定義でも表示と実戦結果が変わり、固有性監査も正しくできない。

- `ONCE_PER_TURN` / `ONCE_PER_BATTLE` は、現在は各stepの条件判定より前に使用済みフラグが立つため、条件不成立でも使用回数を消費する。
- EVENTの `ONCE_PER_BATTLE` は実行時の `play-<serial>` がメモリキーに入るため、同じカードを再使用すると別インスタンス扱いになり、実質的に「1戦1回」にならない。
- SUPPORTの `DEFEAT` は、同レーンの味方UNITが退場した時にも呼ばれる。用語説明の「このカードが相手ユニットを撃退した直後」と意味が一致していない。
- `KILL_DRAW` は「各ターン1回」と表示するが、現行処理にはターン内回数制限がない。
- `DAMAGE_WARD` は「各相手ターン、最初に受けるダメージ」を軽減すると表示するが、現行処理は耐久が残る限りダメージを受けるたびに軽減し、毎回耐久を1消費する。
- `THORNS` は戦闘ダメージがシールド等で0になっても、戦闘扱いなら反射が発生し得る。
- `BREAK_SUPPORT` の `ENEMY_ANY` / `ENEMY_ALL` はUNIT用のレーン抽出を流用しており、敵UNITがいない「サポートだけのレーン」を正しく対象にできない。
- 撃破元の判定が正面レーンの味方UNITを前提にしているため、EVENTやDSLの遠隔ダメージで敵を倒した場合でも、正面UNITの `KILL_DRAW` / `DEFEAT` が誤って発動する可能性がある。

固有効果の設計では「誰が発動したか」「何を対象にしたか」「何回まで使えるか」を効果データに明示し、エンジン側もその情報を保持して解決する。

## 5. 「唯一無二」と判定する基準

次の条件をすべて満たして初めて「固有化完了」とする。

1. **数値違いだけでは別効果と数えない。**
2. **発動タイミング違いだけでも、プレイ判断が同じなら別効果と数えない。**
3. カードを使う前に考えること、使った後の盤面変化、狙う勝ち筋のどれかが他カードと異なる。
4. カード名・キャラクター・題材から効果の意味を説明できる。
5. その効果が実際のエンジンで有効に働き、死にstepを含まない。
6. UIの説明文と実際の処理が一致する。
7. CPUが使用価値を評価できる。

### 固有性として認めない例

- A: 敵に3ダメージ / B: 敵に4ダメージ
- A: 味方を2回復 / B: 味方を3回復
- A: シールド2 / B: シールド3
- 同じ2stepで `duration` だけ違う
- `effectId` や `memoryKey` だけ違う

### 固有性として認める例

- 攻撃前に別レーンへ移動すると追加攻撃できる
- 中央レーンを空けることで左右の味方を同時強化する
- 敵サポートを破壊した場合だけ、その耐久分をシールドへ変換する
- 自分のライフが半分以下の時だけ、回復ではなく攻撃へ効果が反転する
- 同じレーンで2ターン生存すると記録が完成し、次の直接攻撃が強化される

## 6. Editionごとの設計方針

584枚をランダムな組み合わせで差別化するのではなく、Editionごとにプレイ感を分ける。

### ELEMENTARY

- 1枚を読めばすぐ分かる効果を優先する
- レーン位置、登場、攻撃、回復、守る、移動を中心にする
- 複雑な記録・複数ターン予約は少なめにする
- 「カード名を見れば何をしそうか想像できる」ことを最優先する

### HIGH_SCHOOL

- SP差、手札、サポート連携、位置交換、撃破条件などを増やす
- 2枚以上の組み合わせで強くなるカードを用意する
- リスクとリターン、手札循環、コンボ起点を明確にする

### MAGIC

- MARK、変化、蓄積、連鎖、全体効果など高度な仕組みを担当する
- 2step効果を積極的に使う
- 条件達成時の大きな逆転や盤面変化を許容する
- 強力な代わりに条件、回数制限、SP要求などを付ける

## 8. DSLに追加を検討する効果語彙

既存14 actionだけでも組み合わせは多いが、584枚を意味のある形で差別化するには、次の拡張候補を優先検討する。

| 候補 | 用途 |
| --- | --- |
| `READY` | 攻撃済みユニットを再行動可能にする |
| `SWAP` | 2レーンのユニットを入れ替える |
| `PUSH` / `PULL` | 敵ユニットを隣接レーンへ動かす |
| `RETURN_HAND` | 味方または敵を手札へ戻す |
| `REVIVE` | 捨て札のUNITを条件付きで戻す |
| `TUTOR` | 条件に合うカードを山札から探す |
| `COST_MOD` | カードのSPコストを一時変更する |
| `COPY_EFFECT` | 条件付きで直前または同レーンの効果を複製する |
| `STEAL_SP` | 相手SPを減らし自分へ移す |
| `TOKEN` | 一時ユニット / 一時サポートを生成する |
| `TRAP` | 相手の特定行動を待って発動する |
| `SPLASH` | 隣接レーンにも波及する |
| `REFLECT` | 受けた効果の一部を返す |
| `TRANSFORM` | 条件達成でカード状態を変化させる |

追加するactionは、表示文・CPU評価・対象選択・セーブ互換・テストまで同時に実装する。

## 9. 各カードの再設計台帳

実装時は584枚すべてについて、次の1行を必ず作る。**行がないカードは未設計扱い**とする。

| No. | Card ID | 名称 | Edition | 種別 | 現行legacy | 現行DSL | 新しい固有コンセプト | 新効果文 | 他カードとの差 | エンジン追加 | 状態 |
| ---: | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 |  |  |  |  |  |  |  |  |  |  | `未設計` |

台帳は `PLACEMENT_TCG_CARDS` をVite SSRで実体化して初期生成する。最低限、次の現在値を自動出力する。

- `id`
- `name`
- `edition`
- `kind`
- `spCost`
- `attack` / `health` / `durability`
- `effect`
- `amount`
- `rulesText.jp`
- `effectProgram.trigger`
- `effectProgram.resetRule`
- 全 `steps` の `action / target / condition / amount / duration`

その後、`新しい固有コンセプト`、`新効果文`、`他カードとの差` を人が1枚ずつ決める。

## 10. 1枚ごとの設計手順

各カードは次の順で決める。

1. 名前・イラスト・キャラクター性から「何をするカードか」を1文で決める。
2. UNIT / SUPPORT / EVENTの役割に合う主triggerを決める。
3. プレイヤーにどんな判断を要求するかを決める。
4. 盤面・手札・SP・ライフのどれを動かすか決める。
5. 同じ役割の既存カードを検索する。
6. 数値を消して比較しても別の体験になることを確認する。
7. 必要ならDSL action / target / conditionを追加する。
8. 日本語・英語・ひらがなの表示文を合わせる。
9. CPU評価値を追加する。
10. 正常系と境界系を最低1件ずつテストする。

EVENTは対象選択と盤面変化を強くし、同じ「ダメージ」「回復」「ドロー」の数値違いに戻さない。

## 12. 実装方針

現在の `buildPlacementEffectProgram()` のindex自動生成は、固有化完了後の本番カード効果生成には使わない。

推奨形は次のどちらかとする。

### A. カード定義内に明示的なeffectProgramを書く

カードを見れば効果定義まで追える。584枚の定義は長くなるが監査しやすい。

### B. `placementTcgUniqueEffects.ts` にCard ID → effectProgramを集約する

```ts
const PLACEMENT_TCG_UNIQUE_EFFECTS: Record<string, PlacementEffectProgram> = {
  MTCG_...: { ... },
};
```

584枚を一覧監査しやすいため、現状ではBを推奨する。

`effectId` は単なる通し番号ではなく、カードの意味が分かる安定IDへ変えてよい。

例:

```text
EFFECT_GON_AMBUSH
EFFECT_MELOS_LAST_SPRINT
EFFECT_CENTER_LANE_COMMAND
```

## 14. 意味シグネチャ

現在の `normalizedSignature` だけでは、実際に使われない `duration` なども差分になる。固有性監査用に別の意味シグネチャを用意する。

例:

```text
kind
edition
trigger
resetRule
playerDecisionType
boardMutationType
resourceMutationType
targetSelectionType
conditionFamily
payoffFamily
```

数値は原則として意味シグネチャから除外する。同じ意味シグネチャになったカードは、自動的に「再設計対象」とする。

## 15. バランス調整の考え方

「唯一無二」を優先しても、カードパワーまで無制限に上げない。

- 1 SP: 単純効果、準備、軽い位置操作
- 2 SP: 1効果 + 小さな副効果
- 3 SP: 明確な盤面変化、条件付き高効率
- 4 SP: 強いコンボ、複数対象、再行動
- 5 SP以上のUNIT: 勝ち筋になり得る固有能力

強い固有効果には、SP、条件、回数制限、耐久消費、位置制限のいずれかを付ける。
